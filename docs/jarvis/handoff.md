# Передача работы: что дальше

**Машиночитаемая версия: [handoff.json](handoff.json)** — точное место остановки,
версии, гипотезы и команды.

Документ для сессии, которая продолжает работу на Windows-машине. Слой Jarvis
писался и проверялся в Linux-контейнере без Windows, микрофона и экрана —
поэтому всё, что осталось, упирается именно в платформу.

Ветка: `claude/jarvis-workstation-vk6nx1`.

## Первое, что стоит сделать

Установка на Windows **ни разу не выполнялась вживую**. Это самый большой
непроверенный кусок, и всё остальное строится поверх него.

```powershell
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/aisarus/Rujarvis/claude/jarvis-workstation-vk6nx1/install.ps1))) -Branch claude/jarvis-workstation-vk6nx1
```

Первый живой прогон дошёл до `pnpm install` и упал на двух вещах, обе
исправлены, но заново не проверены:

- На машине стоял Node 24, а проект требует ровно 22.x. Проверка смотрела
  только нижнюю границу, поэтому пропускала — падало гораздо позже, на сборке
  нативных модулей.
- Не было Visual Studio Build Tools с нагрузкой C++, без которых `node-gyp` не
  соберёт `interpreter-window-pin`, `node-pty` и `uiohook-napi`.

Второй прогон прошёл дальше: Node 22.22.1 через fnm, MSVC найден, 1680 пакетов
встали, `interpreter-window-pin` собрался. Упало на `postinstall` репозитория —
`electron-rebuild -f -w node-pty,uiohook-napi,interpreter-window-pin`, MSBuild
вернул ошибку в `Microsoft.CppBuild.targets`.

Важное наблюдение: node-gyp под Node headers **работает** (window-pin собрался),
падает именно пересборка под Electron headers. Значит MSVC на месте, дело в
чём-то другом.

Третий промах того же вида: pnpm был 11.11.0, а проект закрепляет 9.15.9.
Установщик проверял наличие, а не версию — ровно как до этого с Node. Исправлено
(`Assert-PnpmVersion`), но заново не проверено.

Точное состояние, гипотезы и порядок действий — в [handoff.json](handoff.json).

Дальше есть чем проверить сам слой без микрофона:

```bash
pnpm run jarvis:try                                    # диалог русской речью
pnpm run jarvis:try -- --dry "почини билд в аегисе"    # только разбор
```

## Что осталось, по порядку

1. **Глобальная горячая клавиша** → `VoiceSession.pressPushToTalk()` /
   `releasePushToTalk()`. Автомат состояний готов и покрыт тестами
   (`jarvis/voice/session.ts`), нужен только `globalShortcut` в Electron main.
   В upstream `globalShortcut` не используется нигде — регистрации нет вообще.
2. **Захват звука** → реализовать интерфейсы `AudioCapture` и `Transcriber`
   из `jarvis/voice/session.ts` поверх существующего аудиоконвейера
   Workstation и `WhisperRecognizer`.
3. **Трей и оверлей.** Оверлей читает `VoiceSession.status` — там уже есть
   `idle / listening / transcribing / thinking / working / speaking` и готовая
   русская подпись. `electron/trayMenu.ts` существует, но Jarvis в нём нет.
4. **Переключатель backend-ов** в настройках (`Main brain` / `Coding`).
   Требует персистентности настроек Jarvis — сейчас `JarvisSettings` живёт
   только в памяти, в `configStore` его нет.
5. **Живая проверка русского распознавания** на настоящей речи.

Точка сборки всего — `createJarvis()` в `server/jarvis/createJarvis.ts`.
Приложение её пока не вызывает; это и есть недостающее звено между готовым
ядром и интерфейсом.

## Грабли, на которые уже наступили

Стоили времени, повторять не надо.

**sherpa-onnx в npm — это WebAssembly-сборка.** Три следствия, все проверены
запуском:

- Один экземпляр модуля на процесс. Создать в одном процессе движок синтеза и
  движок распознавания нельзя — модуль падает с голым числом вместо ошибки.
  Поэтому распознавание живёт в своём worker-потоке (`whisperRecognizer.ts`),
  как синтез в upstream.
- Сборка однопоточная. `numThreads` больше 1 роняет загрузку.
- `acceptWaveform(sampleRate, samples)` — позиционные аргументы, не объект.
  Сэмплы 16 кГц, float в диапазоне [-1, 1].

**Авторизация CLI трёхзначная, и это не случайность.** Проверка файла
учётных данных даёт ложное «вход не выполнен» при host-managed установках,
ключах из переменных окружения и корпоративных шлюзах — CLI при этом
прекрасно работает. См. `jarvis/backends/authHints.ts`. Не упрощать обратно
до булева значения.

**Отрицание разрешается внутри клаузы, а не по всей реплике.** В «…ничего не
меняй. Через Клод Код.» частица «не» относится к «меняй». Пока это не было
учтено, работа уходила не тому backend-у. См. `splitClauses` в
`jarvis/router/text.ts`.

**Codex на недоступной сети не завершается сам.** Повторяет попытки,
переключает транспорт и ждёт сеть без собственного терминального события.
Поэтому в `jarvis/backends/codex.ts` есть счётчик попыток подряд, который
завершает запуск с внятной причиной.

**Электронные скриншоты под xvfb не работают** — если тесты запускаются в
Linux-CI, захват кадра и видео отваливается по таймауту. На Windows это,
скорее всего, не проблема.

## Что нельзя ломать

Эти инварианты держатся кодом и покрыты тестами. Если рефакторинг их
нарушает — неправильный рефакторинг.

- **Нормализация только сужает разрешения.** Ни правила, ни модель не могут
  расширить конверт. `assertNormalizationIsSafe` падает, если попытались.
- **Исходная реплика всегда доходит до backend-а** дословно, рядом с
  нормализованной целью, а не вместо неё.
- **Классификация риска — чистая функция от действия.** Оценка риска от
  модели может поднять класс, но никогда не понизить.
- **Локальная модель-маршрутизатор необязательна.** Любой сбой возвращает
  `null` и падает обратно на правила. У её ответа нет поля, которым можно
  выдать разрешение, выбрать backend или понизить риск.
- **Ошибка backend-а — это результат, а не исключение.** Адаптер не имеет
  права уронить процесс.
- **Fallback только на отказ самого backend-а** (исчерпан лимит, нет CLI,
  процесс умер молча). Честное «не смог, вот почему» — это ответ, а не повод
  спросить то же самое у другого поставщика.

## Проверки

```bash
pnpm typecheck
pnpm run test:vitest        # 647 зелёных, из них 284 — слой Jarvis
pnpm run test:unit          # 36 падений, идентичных чистому upstream в Linux-контейнере
pwsh -File scripts/check-install-script.ps1
```

Про `test:unit`: 36 падений были один в один такими же на чистом
`upstream/main` в том же контейнере — это среда, а не регрессия. На Windows
картина может отличаться, стоит перепроверить базу тем же способом
(worktree на `upstream/main` и сравнение списков).

## Правки в файлах upstream

Их семь, все точечные и прокомментированы на месте. Список с оценкой риска
конфликта — в [upstream-sync.md](upstream-sync.md). Почти весь код Jarvis
лежит в `jarvis/` и `server/jarvis/`, которых в upstream нет, поэтому
`git pull upstream main` должен оставаться дешёвым. Если при слиянии
приходится подстраивать upstream под форк — скорее всего, менять нужно
`jarvis/`.
