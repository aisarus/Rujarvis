# Автопилот: задача на самостоятельную работу

Этот файл — задача для Claude Code, работающего над Rujarvis без присмотра
(`/loop`). Он читается в начале каждого витка и дописывается в конце. Всё
остальное — `AGENTS.md`, `README.md`, `docs/jarvis/architecture.md`,
`docs/jarvis/handoff.md` — остаётся в силе.

Цель одна: **Rujarvis работает у чужого человека на Windows и на маке с
первой минуты — от команды установки до голоса, окон, браузера и агента — и
не ломается**. Сначала надёжность того, что есть, потом развитие.

---

## Три условия, которые важнее любой задачи

Нарушено хоть одно — всё прочее откладывается, пока не восстановлено.

### 1. GitHub и машина владельца всегда синхронны

После каждого пуша установка на машине владельца стоит на том же коммите и
пересобрана.

Приёмка:

```bash
git fetch origin main
test "$(git -C "$LOCALAPPDATA/Rujarvis/src" rev-parse HEAD)" = "$(git rev-parse origin/main)"
git -C "$LOCALAPPDATA/Rujarvis/src" status --short   # пусто
```

и `dist/app/main.cjs` установки новее коммита. Обновление — только так:
`git -C … reset --hard origin/main` (сначала убедиться, что `status --short`
пуст: чужие правки не трогать), затем `pnpm install --frozen-lockfile` и
`pnpm build` в папке установки. Виток не заканчивается с незакоммиченным в
рабочей копии.

### 2. Windows и мак всегда синхронны

Каждая возможность либо работает на обеих системах, либо на одной из них
честно отвечает «нечем мерить» или «не поддерживается» — и это проверено
тестом, а не обещано.

Приёмка: на HEAD зелёные все три прогона GitHub — `CI`, `Install on
Windows`, `Install on macOS`. Новая живая проверка ставится в оба
`.github/workflows/install-*.yml` либо в её шапке сказано, почему она только
для одной системы, и на другой она выходит с кодом 2.

### 3. Установщик, онбординг и основа не ломаются

Основа — это то, без чего Джарвиса нет: красные линии (стоп, тишина, пауза,
продолжай — на обоих языках), прямые команды, запуск и закрытие программ,
окна, браузер, путь через агента, вход в Claude Code и Codex.

Приёмка перед каждым пушем:

```bash
pnpm typecheck && pnpm typecheck:tests && pnpm test && pnpm build
```

и после пуша — три прогона GitHub зелёные. Покраснел — это следующая
задача, раньше любой другой.

## Как работать (уроки, оплаченные поломками)

1. **Сначала воспроизвести настоящим путём, потом чинить.** 26.09.2026
   «починка» по пробе, мерившей не ту ветку кода, сломала запуск Edge у
   владельца. Баг, который не воспроизведён через настоящую точку входа
   (журнал живого прогона, голосовой путь, MCP-сервер, `handleUtterance`), не
   чинится.
2. **Только замеренное.** Таблицы ослышек, пороги, умолчания меняются по
   замеру. Шумный замер (синтез голоса, ответ модели) — минимум два-три
   прогона: один прогон 26.09 соврал.
3. **У каждой правки — тест, который падает на старом коде.** Зубы
   проверяются временной правкой и возвратом байт-в-байт. Никогда
   `git checkout --` поверх незакоммиченного: так однажды стёрся час работы.
4. **Три ответа, а не два:** прошло, не прошло, нечем мерить. Отчёт об успехе
   того, чего не было, — баг.
5. **Не красть фокус у владельца.** Проверки, выводящие окна вперёд
   (`cua-check`, `qa`, `hands-check`, `browser-keys-check`), гоняются в CI. На
   машине владельца — только то, что окон не трогает, либо ночью.
6. **Чужое не трогать.** Гасить только свои pid, записанные при запуске.
   Никогда не удалять `Desktop\Джарвис`, `~/.claude`, `~/.codex`, окна и
   вкладки браузера владельца.
7. **Только подписки.** Никаких ключей API, телеметрии, облачных шлюзов.
8. **Тест, ждущий неверного, не удаляется молча.** Если тест закреплял
   ошибку, в сообщении коммита сказано, какую и почему ожидание меняется.
9. **Решение за владельцем — не принимается.** Всё, что меняет привычное
   поведение (умолчания, смысл команд, что гасит «стоп»), уходит в раздел
   «Вопросы владельцу» ниже, и виток идёт к следующему пункту.
10. **Один смысл — один коммит.** `git commit -s`, сообщение по-русски: что
    сломалось, как замерено, что сделано, чем проверено. Комментарии в коде —
    по-русски и про «почему».
11. **Проверочные прогоны — мимо данных владельца.** `jarvis:try` на его
    машине — только с `--probe`; живые проверки — со своей временной папкой
    данных и памяти (`agent-check` так и сделан). 27.09.2026 без этого восемь
    проверочных задач легли в его память, а заметка — в память агента.

## Как устроен виток

1. `git pull`. Проверить три прогона GitHub на HEAD. Красный — чинить его.
2. Проверить синхронность с машиной (условие 1). Нет — довести.
3. Взять первый незакрытый пункт ниже по порядку.
4. Воспроизвести → починить → тест с проверкой зубов → проверить настоящим
   путём → документация.
5. Проверки перед пушем → коммит → пуш → дождаться трёх прогонов GitHub →
   обновить установку владельца → проверить синхронность.
6. Отметить пункт: `[x]`, коммит, замер. Дописать строку в «Журнал».
7. Пункты кончились — раздел «Развитие»: сначала дописать туда план с
   приёмкой, потом делать.
